# แผนงาน: สมัครสมาชิก / เข้าสู่ระบบ

อ้างอิง: SPEC-สมัครสมาชิก-เข้าสู่ระบบ-002 (Draft v2)

## 1. สรุปแนวทาง

- รองรับผู้ใช้ที่มีบัญชีเข้าสู่ระบบ และผู้ที่ยังไม่มีบัญชีสมัครสมาชิก โดยรายละเอียดสมัครสมาชิกยังรอ Q-05 (ASM-01, Q-05)
- ตรวจสอบตัวตนก่อนให้เข้าถึงฟังก์ชันส่วนบุคคล และจำกัดการเข้าถึงตามสิทธิ์ของบทบาท (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-01, FR-สมัครสมาชิก-/-เข้าสู่ระบบ-04, Constraints: การควบคุมสิทธิ์, Q-02)
- เมื่อข้อมูลเข้าสู่ระบบไม่ถูกต้อง แสดงข้อความตามข้อกำหนดและเปิดให้กรอกใหม่ (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-02, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-02)
- รองรับการเปลี่ยนรหัสผ่านโดยใช้ข้อมูลนักศึกษาเพื่อยืนยันตัวตนผ่าน “ลืมรหัสผ่าน” (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-03, ASM-02, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-03)
- วางแผน timeout 10 นาทีตาม NFR-SEC-02 แต่รายละเอียดกิจกรรมที่นับเป็นการใช้งานยังรอคำตอบ (NFR-SEC-02, ASM-04, Q-06)

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) สำหรับหน้าบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นตามรายวิชาใน prompt /plan; ไม่มี Constraint ระบุเทคโนโลยี |
| Python FastAPI สำหรับหลังบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นตามรายวิชาใน prompt /plan; ไม่มี Constraint ระบุเทคโนโลยี |

## 3. โมเดลข้อมูล

ข้อเสนอนี้เป็นแบบจำลองเชิงแนวคิด; รายละเอียดข้อมูลยืนยันตัวตน/สิทธิ์และการสมัครสมาชิกต้องรอคำตอบ Q-01, Q-02 และ Q-05

| Entity | ฟิลด์หลักที่เสนอ | รองรับ |
|---|---|---|
| Account | username, password verifier, role reference | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-01, FR-สมัครสมาชิก-/-เข้าสู่ระบบ-04, NFR-SEC-01; การเปิดบัญชีใหม่รอ Q-05 |
| StudentRecordReference | ข้อมูลอ้างอิงนักศึกษาสำหรับยืนยันตัวตน (ฟิลด์จริงยังไม่ระบุ) | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-03, Constraint: ต้องมีข้อมูลนักศึกษาในระบบมหาวิทยาลัย, Q-01 |
| AuthSession | account reference, last activity timestamp | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-01, FR-สมัครสมาชิก-/-เข้าสู่ระบบ-04, NFR-SEC-02, Q-06 |
| RolePermissionMapping | บทบาทและการอ้างอิงสิทธิ์เข้าถึงฟังก์ชัน (รายการจริงยังไม่ระบุ) | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-04, Constraint: ควบคุมสิทธิ์ตามบทบาท, Q-02 |

ยังไม่กำหนดฟิลด์ข้อมูลนักศึกษา, รายการบทบาท/สิทธิ์ หรือการจัดเก็บข้อมูลสำหรับสมัครสมาชิก จนกว่าจะได้คำตอบที่เกี่ยวข้อง (Q-01, Q-02, Q-05). รายละเอียดการปกป้องข้อมูลบัญชีต้องผ่านเกณฑ์ความปลอดภัยที่ทีมกำหนด (NFR-SEC-01, Q-03).

## 4. API / หน้าจอ

รายการต่อไปนี้เป็นข้อเสนอทางเทคนิคเพื่อรองรับ FR ที่มีอยู่ ไม่ได้เพิ่มข้อกำหนดใหม่

| รายการ | Method / path หรือ input/output หลัก | รองรับ |
|---|---|---|
| เข้าสู่ระบบ | `POST /api/auth/login`; input: รหัสนักศึกษา/อีเมลและรหัสผ่าน; output: ผลยืนยันตัวตนและหน้าหลักเมื่อสำเร็จ | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-01, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-01 |
| เข้าสู่ระบบด้วยข้อมูลผิด | ใช้ `POST /api/auth/login`; input: ข้อมูลเข้าสู่ระบบ; output: ข้อความ “รหัสผ่านหรือชื่อผู้ใช้ไม่ถูกต้อง” และให้กรอกใหม่ | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-02, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-02, ASM-03 |
| เปลี่ยนรหัสผ่าน | `POST /api/auth/password-reset`; input: ข้อมูลนักศึกษา; output: ผลยืนยันตัวตนและการอนุญาตให้ดำเนินการเปลี่ยนรหัสผ่าน | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-03, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-03, ASM-02 |
| หน้าสมัครสมาชิก | ยังไม่กำหนด method/path, input/output จนกว่าจะยืนยันข้อมูลและขั้นตอนสมัครสมาชิก | ASM-01, Q-05 |
| การเข้าถึงฟังก์ชันและหมดอายุ session | ตรวจสิทธิ์ก่อนเข้าถึงฟังก์ชัน; หมดอายุเมื่อ idle ครบ 10 นาที โดยนิยาม idle รอคำตอบ | FR-สมัครสมาชิก-/-เข้าสู่ระบบ-04, NFR-SEC-02, Constraints: การควบคุมสิทธิ์, Q-02, Q-06 |

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ไม่มี ID: ผู้ใช้ต้องมีบัญชีที่ถูกต้องหรือมีข้อมูลนักศึกษาอยู่ในระบบมหาวิทยาลัย | แนวคิด `Account` และ `StudentRecordReference`; ยังไม่กำหนดแหล่ง/ข้อมูลตรวจสอบจนกว่าจะได้คำตอบ Q-01 และรายละเอียดสมัครสมาชิกจาก Q-05 | ยังไม่ได้ใช้ เพราะยังระบุข้อมูลและแหล่งตรวจสอบไม่ได้ (Q-01, Q-05) |
| ไม่มี ID: ต้องควบคุมสิทธิ์การเข้าถึงข้อมูลตามบทบาทผู้ใช้ | แนวคิด `RolePermissionMapping` และตรวจสิทธิ์ก่อนเข้าถึงฟังก์ชัน; รายการบทบาทและสิทธิ์รอคำตอบ Q-02 | ยังไม่ได้ใช้ เพราะยังไม่ทราบบทบาทและสิทธิ์ที่ต้องกำหนด (Q-02) |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-สมัครสมาชิก-/-เข้าสู่ระบบ-01 | `test_AC_สมัครสมาชิก_เข้าสู่ระบบ_01` | ใช้บัญชีที่ถูกต้อง กรอกรหัสนักศึกษา/อีเมลและรหัสผ่านที่ถูกต้อง ตรวจว่าเข้าสู่ระบบสำเร็จและแสดงหน้าหลัก (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-01, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-01) |
| AC-สมัครสมาชิก-/-เข้าสู่ระบบ-02 | `test_AC_สมัครสมาชิก_เข้าสู่ระบบ_02` | ส่งข้อมูลเข้าสู่ระบบที่ไม่ถูกต้อง ตรวจว่าไม่อนุญาตให้เข้าสู่ระบบ แสดงข้อความตามกำหนด และให้กรอกข้อมูลใหม่ได้ (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-02, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-02) |
| AC-สมัครสมาชิก-/-เข้าสู่ระบบ-03 | `test_AC_สมัครสมาชิก_เข้าสู่ระบบ_03` | เลือก “ลืมรหัสผ่าน” และส่งข้อมูลนักศึกษา ตรวจว่าระบบใช้ข้อมูลเพื่อยืนยันตัวตนและอนุญาตให้ดำเนินการเปลี่ยนรหัสผ่าน (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-03, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-03) |

การทดสอบสมัครสมาชิกยังจัดทำไม่ได้เพราะไม่มี AC สำหรับพฤติกรรมดังกล่าว; รอคำตอบและข้อกำหนดที่ทีมยืนยัน (ASM-01, Q-05). การทดสอบสิทธิ์ตามบทบาทและ NFR-SEC-01/02 ต้องระบุเกณฑ์และเงื่อนไขทดสอบเพิ่มเติมก่อน (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-04, NFR-SEC-01, NFR-SEC-02, Q-02, Q-03, Q-06).

## 7. ลำดับงาน

1. ยืนยันข้อมูล/แหล่งตรวจบัญชีและข้อมูลนักศึกษาก่อนกำหนดการยืนยันตัวตน (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-01, FR-สมัครสมาชิก-/-เข้าสู่ระบบ-03, Q-01)
2. สรุปขั้นตอน ข้อมูล และเกณฑ์ตรวจรับการสมัครสมาชิกก่อนออกแบบหน้าสมัคร (ASM-01, Q-05)
3. กำหนด mapping ระหว่างบทบาทกับฟังก์ชันที่เข้าถึงได้ (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-04, Q-02)
4. ออกแบบและพัฒนาการเข้าสู่ระบบและตรวจตัวตน (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-01, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-01)
5. พัฒนาการแสดงข้อความกรณีข้อมูลผิดและการกรอกใหม่ (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-02, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-02)
6. ออกแบบขั้นตอนเปลี่ยนรหัสผ่านโดยใช้ข้อมูลนักศึกษา หลังยืนยันรายละเอียดข้อมูลและวิธีตรวจสอบ (FR-สมัครสมาชิก-/-เข้าสู่ระบบ-03, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-03, Q-01)
7. กำหนดเกณฑ์และตรวจการจัดเก็บรหัสผ่าน/ควบคุมสิทธิ์ตามนโยบายที่ทีมระบุ (NFR-SEC-01, Q-03)
8. กำหนดเหตุการณ์ activity, ทดสอบ timeout และรันทดสอบ AC ทั้งสามข้อ (NFR-SEC-02, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-01, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-02, AC-สมัครสมาชิก-/-เข้าสู่ระบบ-03, Q-06)

## 8. สิ่งที่ยังไม่ทำ

- **Q-01** ข้อมูลใดใช้ยืนยันว่าผู้ใช้มีบัญชีที่ถูกต้องหรือเป็นนักศึกษาที่มีข้อมูลในระบบมหาวิทยาลัย และตรวจสอบจากแหล่งใด? ต้องถามทีม/ผู้ดูแลข้อมูลนักศึกษาของมหาวิทยาลัย ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-02** แต่ละบทบาทเข้าถึงฟังก์ชันใดได้บ้าง และ AC ข้อใดใช้ตรวจสอบสิทธิ์ตามบทบาท? ต้องถามทีม/ผู้รับผิดชอบ UC-14 ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-03** ใช้เกณฑ์ใดตรวจสอบว่าการจัดเก็บรหัสผ่านและการควบคุมสิทธิ์เป็นไปตาม NFR-SEC-01? ต้องถามทีม/ผู้รับผิดชอบนโยบายความปลอดภัย ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-04** รายละเอียดนโยบายหรือค่ากำหนดใดใน UC Case.pdf ที่ต้องยืนยัน และ AC แต่ละข้ออ้างอิง FR/NFR ใด? ต้องถามผู้จัดทำ UC Case.pdf/ทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-05** ขั้นตอนสมัครสมาชิกสำหรับผู้ไม่มีบัญชีต้องใช้ข้อมูลและการตรวจสอบใด และจะตรวจรับด้วย AC ใด? ต้องถามทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-06** เหตุการณ์ใดนับเป็นการใช้งานที่เริ่มนับเวลาใหม่สำหรับ NFR-SEC-02? ต้องถามทีม/ผู้รับผิดชอบนโยบายความปลอดภัย ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
