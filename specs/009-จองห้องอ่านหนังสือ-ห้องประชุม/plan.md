# แผนงาน: จองห้องอ่านหนังสือ / ห้องประชุม

อ้างอิง: SPEC-จองห้องอ่านหนังสือ-ห้องประชุม-009 (Draft v2)

## 1. สรุปแนวทาง

- นักศึกษา/สมาชิกที่เข้าสู่ระบบเลือกห้อง วัน เวลาเริ่ม-สิ้นสุด และจำนวนผู้ใช้สำหรับการจอง (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01, Constraints)
- อนุญาตให้เลือกเฉพาะช่วงเวลาที่ยังไม่ผ่านและไม่มีรายการจอง (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01, ASM-01)
- ตรวจสอบความว่างอีกครั้งก่อนบันทึกและยืนยันรายการจองพร้อมล็อกช่วงเวลา (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-02, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-03)
- หากห้องถูกจองก่อน ให้แจ้งว่าไม่ว่างและให้ผู้ใช้เลือกเวลาใหม่พร้อมตรวจสอบซ้ำ (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-04, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-05)
- ป้องกันช่วงเวลาซ้อนตาม Constraints/NFR; รายละเอียด boundary, capacity, concurrent requests และการยืนยันใหม่รอ Q-01 ถึง Q-06 (NFR-CONC-01, NFR-DATA-01, Q-01 ถึง Q-06)

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) สำหรับหน้าบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นรายวิชาตาม prompt /plan; ไม่มี Constraint ระบุเทคโนโลยี |
| Python FastAPI สำหรับหลังบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นรายวิชาตาม prompt /plan; ไม่มี Constraint ระบุภาษา/framework |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลักที่เสนอ | รองรับ |
|---|---|---|
| Room | room reference, room name/type, capacity (การใช้ตรวจสอบรอ Q-02) | FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01, Q-02 |
| RoomReservation | room reference, member reference, date, start time, end time, user count, reservation status | FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01 ถึง FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-05, NFR-CONC-01, NFR-DATA-01 |
| Member | authenticated member reference | Constraints: ผู้ใช้ต้องเข้าสู่ระบบ, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01 |

RoomReservation ต้องป้องกันการบันทึกช่วงเวลาซ้อนกันสำหรับห้องเดียวกัน; นิยามเวลาที่ปลายช่วงชนกันและการจองพร้อมกันรอคำตอบ Q-01/Q-03 (Constraints, NFR-CONC-01, NFR-DATA-01, Q-01, Q-03).

## 4. API / หน้าจอ

รายการ method/path เป็นข้อเสนอระดับ plan เท่านั้น; ไม่รวมติดตามหรือยกเลิกการจองซึ่งอยู่นอกขอบเขต

| รายการ | Method / path หรือ input/output หลัก | รองรับ |
|---|---|---|
| ตรวจสอบความว่างก่อนจอง | `GET /api/rooms/{roomId}/availability`; input: date, start time, end time; output: ผลว่าง/ไม่ว่าง | FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-02, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-04 |
| ยืนยันและสร้างรายการจอง | `POST /api/room-reservations`; input: room, date, start/end, user count, confirmation; output: รายการจอง/ผลไม่ว่างและให้เลือกเวลาใหม่ | FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-02, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-03, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-05 |
| หน้าสร้างการจอง | input: ห้อง วันที่ เวลาเริ่ม-สิ้นสุด จำนวนผู้ใช้; output: ผลตรวจความว่างและการยืนยัน หรือแจ้งไม่ว่างเมื่อผู้อื่นจองก่อน | FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01 ถึง FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-05 |

ขั้นตอนหลังเลือกเวลาใหม่ว่าจะให้ยืนยันอีกครั้งหรือไม่ยังรอ Q-04; API นี้ยังไม่ตัดสิน behavior ดังกล่าว (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-04, Q-04).

## 5. ตารางตรวจ Constraints

Constraints ใน spec ไม่มี ID เฉพาะ จึงอ้างอิงด้วยข้อความ Constraint ภายใต้ SPEC-จองห้องอ่านหนังสือ-ห้องประชุม-009

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ไม่มี ID: ผู้ใช้ต้องเข้าสู่ระบบและห้องต้องว่าง | ใช้ authenticated member context และตรวจความว่างก่อนบันทึก (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-02, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-03) | ใช้แล้ว |
| ไม่มี ID: ห้องเดียวกันต้องไม่ถูกจองซ้อนในช่วงเวลาเดียวกัน | ตรวจช่วงเวลาของ RoomReservation ก่อนบันทึกและระบุข้อห้าม overlap ในแบบจำลอง; boundary/concurrency ที่แน่นอนรอ Q-01/Q-03 (NFR-CONC-01, NFR-DATA-01) | ใช้แล้ว |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-01 | `test_AC_จองห้องอ่านหนังสือ_ห้องประชุม_01` | ใช้ผู้ใช้ที่เข้าสู่ระบบและห้องว่างในช่วงเวลาอนาคต ยืนยันการจอง ตรวจว่ามีรายการจองและช่วงเวลาถูกล็อก (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01 ถึง FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-03, AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-01) |
| AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-02 | `test_AC_จองห้องอ่านหนังสือ_ห้องประชุม_02` | เตรียมให้ผู้ใช้อื่นจองห้อง/ช่วงเวลาหลังผู้ใช้เริ่มเลือกแต่ก่อนยืนยัน ตรวจว่าระบบแจ้งไม่ว่างและให้เลือกเวลาใหม่ (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-02, FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-05, AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-02) |
| AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-03 | `test_AC_จองห้องอ่านหนังสือ_ห้องประชุม_03` | เปลี่ยนเวลาแล้วตรวจว่าระบบตรวจความว่างของช่วงใหม่ (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-04, AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-03) |

การทดสอบ concurrency ให้ตัดสินผลได้ครบต้องทราบกรณีเวลาขอบเขตและการจัดการคำขอพร้อมกันก่อน (NFR-CONC-01, NFR-DATA-01, Q-01, Q-03).

## 7. ลำดับงาน

1. ยืนยันกติกาว่าช่วงเวลาที่ปลายชนกันนับว่าซ้อนหรือไม่ (Constraints, NFR-CONC-01, NFR-DATA-01, Q-01)
2. ยืนยันว่าต้องตรวจจำนวนผู้ใช้เทียบความจุห้องหรือไม่ (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01, Q-02)
3. รับข้อมูลห้อง/สมาชิก/ช่วงเวลาที่ผู้ใช้เลือก และปฏิเสธเวลาที่ผ่านไปหรือมีรายการจอง (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-01, ASM-01)
4. ตรวจสอบความว่างซ้ำก่อนบันทึก (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-02)
5. บันทึกรายการและล็อกห้อง/ช่วงเวลาเมื่อผู้ใช้ยืนยันและยังว่าง (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-03, AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-01)
6. จัดการกรณีผู้อื่นจองก่อน โดยแจ้งไม่ว่างและให้เลือกเวลาใหม่ (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-05, AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-02)
7. ตรวจช่วงเวลาใหม่และกำหนดว่าต้องยืนยันอีกครั้งตามคำตอบทีม (FR-จองห้องอ่านหนังสือ-/-ห้องประชุม-04, Q-04)
8. ทดสอบ AC ทั้งสามข้อและทดสอบ concurrency หลังได้เกณฑ์การตัดสินคำขอ (AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-01 ถึง AC-จองห้องอ่านหนังสือ-/-ห้องประชุม-03, NFR-CONC-01, NFR-DATA-01, Q-03, Q-05)

## 8. สิ่งที่ยังไม่ทำ

- **Q-01** ช่วงเวลาสองรายการที่เวลาสิ้นสุดและเวลาเริ่มตรงกันพอดีถือว่าซ้อนหรือไม่? ต้องถามทีม/ผู้กำหนดนโยบายการใช้ห้อง ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-02** ระบบต้องปฏิเสธการจองเมื่อจำนวนผู้ใช้เกินความจุห้องหรือไม่? ต้องถามทีม/ผู้ดูแลข้อมูลความจุห้อง ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-03** เมื่อมีคำขอจองพร้อมกันสำหรับห้องและช่วงเวลาเดียวกัน ระบบต้องให้คำขอใดสำเร็จและแจ้งผลกับอีกคำขออย่างไร? ต้องถามทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-04** เมื่อผู้ใช้เลือกเวลาใหม่ ระบบต้องให้ผู้ใช้ยืนยันการจองอีกครั้งหลังตรวจความว่างหรือไม่? ต้องถามทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-05** AC แต่ละข้อควรอ้างอิง FR/NFR ID ใดบ้าง และ AC-01 ควรตรวจการป้องกันการจองพร้อมกันอย่างไร? ต้องถามทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-06** มีนโยบายหรือค่ากำหนดใดใน UC Case.pdf ที่ต้องยืนยันสำหรับการจองห้อง? ต้องถามผู้จัดทำ UC Case.pdf/ทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
