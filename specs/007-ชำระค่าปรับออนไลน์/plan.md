# แผนงาน: ชำระค่าปรับออนไลน์

อ้างอิง: SPEC-ชำระค่าปรับออนไลน์-007 (Draft v2)

## 1. สรุปแนวทาง

- สมาชิกเริ่มจากตรวจยอดค่าปรับค้างชำระก่อนเข้าสู่ขั้นตอนชำระ (FR-ชำระค่าปรับออนไลน์-01, Constraints: ต้องมีค่าปรับค้างชำระ)
- ระบบส่งคำขอชำระผ่านช่องทางที่ปลอดภัยไปยัง Payment Gateway (FR-ชำระค่าปรับออนไลน์-02, NFR-SEC-01)
- บันทึกการชำระและเปลี่ยนสถานะเป็น “ชำระแล้ว” เฉพาะเมื่อ Gateway ยืนยันสำเร็จ (FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
- เมื่อชำระไม่สำเร็จ คงสถานะค้างชำระและให้ผู้ใช้ลองใหม่; การเปลี่ยนช่องทางมีผลหลังผู้ใช้ยืนยัน (FR-ชำระค่าปรับออนไลน์-04, FR-ชำระค่าปรับออนไลน์-05, ASM-01)
- วิธีรับผลเมื่อ Gateway ไม่ตอบ/ส่งซ้ำ การระบุธุรกรรม รายละเอียดแสดงยอด และ actor ยังรอคำตอบ Q-01 ถึง Q-06 (Q-01 ถึง Q-06)

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) สำหรับหน้าบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นรายวิชาตาม prompt /plan; ไม่มี Constraint ระบุเทคโนโลยี |
| Python FastAPI สำหรับหลังบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นรายวิชาตาม prompt /plan; ไม่มี Constraint ระบุภาษา/framework |
| HTTPS สำหรับส่งข้อมูลการชำระ | NFR-SEC-01 | เป็นตัวอย่างช่องทางปลอดภัยที่ spec ระบุ; รายละเอียดการเชื่อมต่อ Gateway รอ Q-01/Q-02 |

## 3. โมเดลข้อมูล

แบบจำลองเชิงแนวคิดเท่าที่จำเป็นต่อ FR; ไม่กำหนดข้อมูลอ่อนไหวหรือรูปแบบข้อมูล Gateway ที่ spec ยังไม่ระบุ (Q-02, Q-04)

| Entity | ฟิลด์หลักที่เสนอ | รองรับ |
|---|---|---|
| FineBalance | member reference, outstanding amount, fine status | FR-ชำระค่าปรับออนไลน์-01, Constraints: ต้องมีค่าปรับค้างชำระ |
| PaymentAttempt | fine reference, amount, selected channel, payment status, gateway transaction reference (รูปแบบรอ Q-02) | FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, FR-ชำระค่าปรับออนไลน์-04, FR-ชำระค่าปรับออนไลน์-05, NFR-REL-01, Q-02 |
| PaymentChannel | channel identifier/label ที่ให้ผู้ใช้เลือกก่อนยืนยัน | FR-ชำระค่าปรับออนไลน์-05, ASM-01 |

ไม่กำหนดอัตราค่าปรับหรือจำนวนวันเกินกำหนดในฟีเจอร์นี้ เพราะการคำนวณค่าปรับอยู่นอกขอบเขต; ใช้ยอดค้างชำระที่ระบบมีอยู่แล้ว (Constraints: อัตราและจำนวนวันตามกฎห้องสมุด, Scope: Out of scope UC-12, FR-ชำระค่าปรับออนไลน์-01).

## 4. API / หน้าจอ

ชื่อ method/path เป็นข้อเสนอสำหรับวางแผนเท่านั้น; รูปแบบการรับผล Gateway และการจับคู่ transaction ยังไม่สรุปจนกว่าจะได้ Q-01/Q-02

| รายการ | Method / path หรือ input/output หลัก | รองรับ |
|---|---|---|
| ดูค่าปรับค้างชำระ | `GET /api/me/fines`; input: ผู้ใช้ที่เริ่มคำขอ; output: ยอดค่าปรับค้างชำระ | FR-ชำระค่าปรับออนไลน์-01 |
| เริ่มคำขอชำระ | `POST /api/payments`; input: fine reference และช่องทางที่ผู้ใช้ยืนยัน; output: ผลการส่งคำขอ/ข้อมูลตอบกลับที่จำเป็นจาก Gateway (รายละเอียดรอ Q-01/Q-02) | FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-05, NFR-SEC-01 |
| รับผลการชำระ | `POST /api/payments/result` (ข้อเสนอ; วิธีรับผลจริงรอ Q-01/Q-02); input: ผลยืนยันจาก Gateway; output: สถานะการชำระที่บันทึก | FR-ชำระค่าปรับออนไลน์-03, FR-ชำระค่าปรับออนไลน์-04, NFR-REL-01 |
| หน้าชำระค่าปรับ | input: ยอดค้างและช่องทางชำระที่เลือก; output: ยอดก่อนเริ่มชำระ, การยืนยันช่องทาง, ผลสำเร็จ/ไม่สำเร็จและคำแนะนำให้ลองใหม่ | FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-04, FR-ชำระค่าปรับออนไลน์-05, AC-ชำระค่าปรับออนไลน์-01 ถึง AC-ชำระค่าปรับออนไลน์-03, Q-04 |

## 5. ตารางตรวจ Constraints

Constraints ไม่มี ID เฉพาะใน spec จึงอ้างอิงด้วยข้อความ Constraint ภายใต้ SPEC-ชำระค่าปรับออนไลน์-007

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ไม่มี ID: ต้องมีค่าปรับค้างชำระ | แสดงยอดค้างก่อนเริ่มคำขอชำระและผูก PaymentAttempt กับ fine reference (FR-ชำระค่าปรับออนไลน์-01) | ใช้แล้ว |
| ไม่มี ID: ค่าปรับต้องอ้างอิงอัตราและจำนวนวันที่เกินกำหนดตามกฎห้องสมุด | ใช้ยอดค่าปรับที่คำนวณและจัดเก็บตามกฎห้องสมุด; การคำนวณไม่ทำใน UC-07 (Scope: Out of scope UC-12) | ใช้แล้ว |
| ไม่มี ID: ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัย | ส่งข้อมูลผ่าน HTTPS ตาม NFR-SEC-01 | ใช้แล้ว |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-ชำระค่าปรับออนไลน์-01 | `test_AC_ชำระค่าปรับออนไลน์_01` | จำลองกรณีผู้ใช้มียอดค้างและ Gateway ยืนยันสำเร็จ ตรวจว่าระบบบันทึกการชำระและเปลี่ยนสถานะเป็น “ชำระแล้ว”; การผูกผลกับธุรกรรมจริงรอ Q-02 (FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01, Q-02) |
| AC-ชำระค่าปรับออนไลน์-02 | `test_AC_ชำระค่าปรับออนไลน์_02` | จำลอง Gateway แจ้งไม่สำเร็จ ตรวจว่าสถานะยังค้างชำระและระบบแจ้งให้ลองใหม่ (FR-ชำระค่าปรับออนไลน์-04, AC-ชำระค่าปรับออนไลน์-02) |
| AC-ชำระค่าปรับออนไลน์-03 | `test_AC_ชำระค่าปรับออนไลน์_03` | เลือกช่องทางหนึ่ง เปลี่ยนเป็นอีกช่องทางก่อนยืนยัน แล้วยืนยัน ตรวจว่าคำขอใช้ช่องทางใหม่ (FR-ชำระค่าปรับออนไลน์-05, AC-ชำระค่าปรับออนไลน์-03, ASM-01) |

การทดสอบสถานการณ์ Gateway timeout/ผลซ้ำและการตรวจความปลอดภัยในสภาพแวดล้อมที่เชื่อม Gateway จริงอาจทำไม่ได้หากไม่มี sandbox/ข้อมูลทดสอบจากผู้ให้บริการ; วิธีจำลองและรายละเอียดเชื่อมต่อรอ Q-01/Q-02 (NFR-SEC-01, NFR-REL-01, Q-01, Q-02).

## 7. ลำดับงาน

1. ยืนยันรายละเอียดการแสดงยอดค่าปรับและข้อมูลที่ผู้ใช้เห็นก่อนยืนยัน (FR-ชำระค่าปรับออนไลน์-01, Q-04)
2. ยืนยันบทบาท actor และลำดับการเริ่มคำขอระหว่างสมาชิกกับ Gateway (Primary Actor, FR-ชำระค่าปรับออนไลน์-02, Q-03)
3. ตกลงวิธีเชื่อมต่อและจัดการกรณี Gateway ไม่ตอบ/ตอบล่าช้า (FR-ชำระค่าปรับออนไลน์-02 ถึง FR-ชำระค่าปรับออนไลน์-04, Q-01)
4. กำหนดข้อมูลอ้างอิงสำหรับจับคู่ผลยืนยันและแนวทางผลตอบซ้ำ (FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01, Q-02)
5. แสดงยอดค่าปรับค้างและรายการช่องทางที่เลือกได้ก่อนยืนยัน (FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05, ASM-01, Q-04)
6. ส่งคำขอผ่านช่องทางปลอดภัยและประมวลผลผลยืนยันจาก Gateway เท่านั้น (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, NFR-SEC-01, NFR-REL-01)
7. รองรับผลล้มเหลวโดยคงสถานะค้างชำระและให้ลองใหม่ (FR-ชำระค่าปรับออนไลน์-04, AC-ชำระค่าปรับออนไลน์-02)
8. ทดสอบ AC ทั้งสามข้อและทบทวน traceability ตามคำตอบทีม (AC-ชำระค่าปรับออนไลน์-01 ถึง AC-ชำระค่าปรับออนไลน์-03, Q-05)

## 8. สิ่งที่ยังไม่ทำ

- **Q-01** เมื่อ Payment Gateway ไม่ตอบหรือส่งผลล่าช้า ระบบต้องแสดงสถานะใดและผู้ใช้ควรทำอะไรต่อ? ต้องถามทีม/ผู้ดูแลการเชื่อมต่อ Payment Gateway ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-02** ระบบใช้ข้อมูลใดจับคู่ผลยืนยันจาก Gateway กับคำขอและค่าปรับที่ต้องชำระ และจัดการผลยืนยันซ้ำอย่างไร? ต้องถามทีม/ผู้ดูแลการเชื่อมต่อ Payment Gateway ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-03** Primary Actor คือสมาชิกผู้เริ่มชำระ หรือ Payment Gateway ในฐานะระบบภายนอกที่ส่งผลกลับ? ต้องถามทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-04** ต้องแสดงยอดค่าปรับและรายละเอียดใดเพื่อให้ผู้ใช้ยืนยันรายการที่กำลังชำระ? ต้องถามทีม/ผู้รับผิดชอบนโยบายค่าปรับ ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-05** AC แต่ละข้อควรอ้างอิง FR/NFR ID ใด และ AC-01 ควรระบุคำขอที่ส่งให้ Gateway ก่อนการยืนยันผลอย่างไร? ต้องถามทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-06** มีนโยบายหรือค่ากำหนดใดใน UC Case.pdf ที่ต้องยืนยันสำหรับฟีเจอร์นี้? ต้องถามผู้จัดทำ UC Case.pdf/ทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
