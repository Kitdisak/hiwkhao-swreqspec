# แผนงาน: ชำระค่าปรับออนไลน์

อ้างอิง: SPEC-ชำระค่าปรับออนไลน์-007 (Draft v2)

## 1. สรุปแนวทาง (5 บรรทัด)

- สมาชิกดูรายการค่าปรับค้าง รายละเอียดต่อรายการ ยอดรวม และเลือกช่องทางก่อนยืนยัน (FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05)
- ระบบส่งคำขอผูกกับ `payment_ref` และยอดค่าปรับไปยัง Payment Gateway ผ่าน HTTPS (FR-ชำระค่าปรับออนไลน์-02, NFR-SEC-01)
- ผลจาก Gateway ต้องตรวจ ref และยอดก่อนอัปเดตสถานะ; บันทึกผลสำเร็จเพียงครั้งเดียว (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
- จัดการคำขอ Pending, ตรวจสถานะซ้ำด้วย ref เดิม, ป้องกันคำขอซ้ำ และรองรับผลสำเร็จที่มาหลังหมดอายุ (FR-ชำระค่าปรับออนไลน์-04, NFR-REL-01)
- ทดสอบตาม AC เดิมทั้งสามข้อ; ไม่เพิ่ม AC ID และคงประเด็น coverage tests ที่ยังรอคำตอบไว้ใน Q-08

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) สำหรับหน้าบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นของรายวิชา; spec ไม่ได้กำหนด framework |
| Python FastAPI สำหรับหลังบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ค่าเริ่มต้นของรายวิชา; spec ไม่ได้กำหนดภาษา/framework |
| HTTPS สำหรับส่งข้อมูลชำระ | NFR-SEC-01 | เป็นตัวอย่างช่องทางปลอดภัยตาม spec; ไม่เลือกผู้ให้บริการ Gateway แทนทีม |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลักที่เสนอ | รองรับ |
|---|---|---|
| FineItem | fine reference, member reference, book title, due date, returned date, overdue days, outstanding amount, fine status | FR-ชำระค่าปรับออนไลน์-01 |
| PaymentRequest | `payment_ref`, member reference, fine references, total amount, selected channel, request status, created time, expiry time | FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-04, FR-ชำระค่าปรับออนไลน์-05, Constraint: หนึ่งชุดค่าปรับมี Pending ได้ครั้งละหนึ่งคำขอ |
| PaymentResult | `payment_ref`, gateway transaction number, returned amount, result, received time | FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01 |
| PaymentReviewRecord | `payment_ref` ที่ได้รับ, ยอดที่รายงาน, สถานะตรวจสอบ, เหตุผล | FR-ชำระค่าปรับออนไลน์-02; ใช้บันทึกผลที่ ref ไม่พบหรือยอดไม่ตรงเพื่อให้ตรวจสอบ |
| PaymentChannel | channel identifier, display name, selectable status | FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05 |

การคำนวณยอดค่าปรับและอัตราต่อวันไม่อยู่ในฟีเจอร์นี้; อ่านค่าปรับที่คำนวณจากกฎห้องสมุดจากข้อมูล FineItem (Constraints: ค่าปรับอ้างอิงอัตราและวันเกินกำหนด, Scope: Out of scope UC-12, Q-07). ไม่กำหนดฟิลด์ข้อมูลบัตรชำระหรือข้อมูลอ่อนไหวอื่นที่ spec ไม่ได้ระบุ (NFR-SEC-01).

## 4. API / หน้าจอ

| รายการ | Method / path หรือ input/output หลัก | รองรับ |
|---|---|---|
| ดูค่าปรับค้าง | `GET /api/me/fines`; output: รายการพร้อมรายละเอียดและยอดรวม | FR-ชำระค่าปรับออนไลน์-01 |
| เริ่มคำขอชำระ | `POST /api/payments`; input: ช่องทางที่เลือกและยืนยัน; output: `payment_ref` และสถานะคำขอ | FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-05, NFR-SEC-01 |
| รับผลยืนยันจาก Gateway | `POST /api/payments/result`; input: `payment_ref`, ยอด, ผล และเลขธุรกรรม; output: acknowledgement | FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, FR-ชำระค่าปรับออนไลน์-04, NFR-REL-01 |
| ตรวจสถานะคำขอ | `POST /api/payments/{payment_ref}/status-check`; input: ref เดิม; output: สถานะจาก Gateway โดยไม่สร้างคำขอใหม่ | FR-ชำระค่าปรับออนไลน์-04 |
| หน้ารายการ/ยืนยันชำระ | input: รายการ FineItem และช่องทาง; output: รายละเอียดต่อรายการ ยอดรวม และการยืนยันก่อนส่งคำขอ | FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05, AC-ชำระค่าปรับออนไลน์-03 |
| หน้าติดตามสถานะ | input: `payment_ref`; output: Pending/สำเร็จ/ล้มเหลว/หมดอายุ และปุ่มตรวจสอบสถานะเมื่อ Pending | FR-ชำระค่าปรับออนไลน์-03, FR-ชำระค่าปรับออนไลน์-04, NFR-REL-01 |

Endpoints เป็นข้อเสนอระดับแผน; รูปแบบเชื่อมต่อจริงกับ Gateway ยังไม่กำหนด เพราะ spec ไม่ได้ระบุผู้ให้บริการ (FR-ชำระค่าปรับออนไลน์-02, NFR-SEC-01).

## 5. ตารางตรวจ Constraints

Constraints ไม่มี ID เฉพาะใน spec จึงอ้างอิงข้อความ Constraint ภายใต้ SPEC-ชำระค่าปรับออนไลน์-007

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ไม่มี ID: ต้องมีค่าปรับค้างชำระ | แสดงรายการที่ยังค้างและไม่เริ่มคำขอหากไม่มีรายการ (FR-ชำระค่าปรับออนไลน์-01) | ใช้แล้ว |
| ไม่มี ID: ค่าปรับต้องอ้างอิงอัตราและจำนวนวันที่เกินกำหนดตามกฎห้องสมุด | ใช้ยอด FineItem ที่คำนวณและจัดเก็บตามกฎห้องสมุด; ไม่คำนวณอัตราใน UC-07 และคงอัตราต่อวันเป็น Q-07 (Scope: Out of scope UC-12, Q-07) | ใช้แล้ว |
| ไม่มี ID: ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัย | ใช้ HTTPS ในการส่งข้อมูลระหว่างระบบตาม NFR-SEC-01; ไม่กำหนดรายละเอียดของ Gateway แทนทีม | ใช้แล้ว |
| ไม่มี ID: หนึ่งชุดค่าปรับมีคำขอ Pending ได้ครั้งละหนึ่งคำขอ | ป้องกันการเริ่มคำขอซ้ำสำหรับชุดค่าปรับเดิมขณะที่มี PaymentRequest Pending (FR-ชำระค่าปรับออนไลน์-04, FR-ชำระค่าปรับออนไลน์-05) | ใช้แล้ว |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-ชำระค่าปรับออนไลน์-01 | `test_AC_ชำระค่าปรับออนไลน์_01` | สร้างค่าปรับค้างสองรายการรวม 25 บาท; ยืนยันแล้วตรวจว่าคำขอมี `payment_ref` ใหม่และเป็น Pending; จำลองผลสำเร็จจาก Gateway ด้วย ref เดิม ยอดตรง และเลขธุรกรรม; ตรวจค่าปรับเป็นชำระแล้วและยอดค้างเป็นศูนย์ (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01) |
| AC-ชำระค่าปรับออนไลน์-02 | `test_AC_ชำระค่าปรับออนไลน์_02` | จำลอง Gateway ยืนยันล้มเหลว ตรวจคำขอเป็นล้มเหลว ค่าปรับยังค้าง และสมาชิกเริ่มลองใหม่ได้ (FR-ชำระค่าปรับออนไลน์-04, NFR-REL-01) |
| AC-ชำระค่าปรับออนไลน์-03 | `test_AC_ชำระค่าปรับออนไลน์_03` | เปลี่ยนช่องทางก่อนยืนยัน ตรวจรายละเอียดค่าปรับ ยอดรวม และช่องทางที่แสดง; ยืนยันแล้วตรวจว่าคำขอใช้ช่องทางที่เลือก (FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05) |

การทดสอบผลซ้ำและ timeout/หมดอายุยังต้องยืนยันว่าจะผนวกใน AC เดิมข้อใด; ไม่เพิ่ม AC ID ในแผนจนกว่าจะได้คำตอบ Q-08 (FR-ชำระค่าปรับออนไลน์-03, FR-ชำระค่าปรับออนไลน์-04, Q-08). การทดสอบเชื่อม Gateway จริงต้องมี sandbox/ข้อมูลทดสอบจากผู้ให้บริการ; spec ยังไม่ระบุ (FR-ชำระค่าปรับออนไลน์-02, NFR-SEC-01).

## 7. ลำดับงาน

1. เตรียมรายการ FineItem และหน้ารายละเอียดค่าปรับที่อ่านยอดจากข้อมูลเดิม โดยไม่คำนวณค่าปรับใหม่ (FR-ชำระค่าปรับออนไลน์-01, Q-07)
2. ออกแบบ PaymentRequest, ref ไม่ซ้ำ, การผูกสมาชิก/รายการ/ยอด และการป้องกันคำขอ Pending ซ้ำ (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-04, Constraints)
3. สร้างหน้าจอเลือกช่องทางและยืนยัน โดยเปลี่ยนช่องทางได้เฉพาะก่อนยืนยัน (FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05, AC-ชำระค่าปรับออนไลน์-03)
4. ส่งคำขอไป Gateway ผ่าน HTTPS และประมวลผลผลยืนยันโดยตรวจ ref และยอด (FR-ชำระค่าปรับออนไลน์-02, NFR-SEC-01)
5. บันทึกผลสำเร็จ/ธุรกรรมให้เกิดครั้งเดียว; แยกผลที่ ref หรือยอดไม่ตรงไว้ตรวจสอบ (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
6. จัดการ failure, Pending, การตรวจสถานะทุก 5 นาที, อายุคำขอ 30 นาที และการเริ่มใหม่หลังล้มเหลว/หมดอายุ (FR-ชำระค่าปรับออนไลน์-04)
7. รองรับผลสำเร็จที่มาหลังหมดอายุและห้ามผลภายหลังเขียนทับสถานะสำเร็จ (FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
8. ทดสอบ AC-01 ถึง AC-03 และตรวจขอบเขตการส่งข้อมูลผ่าน HTTPS; ติดตาม Q-08 สำหรับ coverage ของผลซ้ำและ timeout (AC-ชำระค่าปรับออนไลน์-01 ถึง AC-ชำระค่าปรับออนไลน์-03, NFR-SEC-01, NFR-REL-01, Q-08)

## 8. สิ่งที่ยังไม่ทำ

- **Q-07** อัตราค่าปรับต่อวันและวิธีคำนวณยอดค่าปรับต่อรายการกำหนดอย่างไร? ต้องถามบรรณารักษ์/ผู้กำหนดนโยบายค่าปรับ ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- **Q-08** จะยืนยันการตรวจผลสำเร็จซ้ำและกรณีไม่มีผลตอบกลับจนคำขอหมดอายุด้วย AC เดิมข้อใด หรือทีมต้องอนุมัติการเพิ่ม AC ใหม่ก่อน? ต้องถามทีม ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
