# Feature: ชำระค่าปรับออนไลน์
Spec ID: SPEC-ชำระค่าปรับออนไลน์-007 | Source: SRS v0.3 | Use case: UC-07
Owner: ทีม หิวข้าว | Status: Draft v2 | Updated: 2569-11-20

## Goal
สมาชิกชำระค่าปรับค้างชำระผ่าน Payment Gateway และระบบบันทึกผลการชำระ

## Primary Actor
สมาชิก

## Secondary Actor
Payment Gateway

## Scope
### In scope
- แสดงรายการค่าปรับค้างชำระ รายละเอียดแต่ละรายการ และยอดรวมก่อนเริ่มชำระ
- ส่งคำขอชำระไปยัง Payment Gateway
- รับผลการชำระและบันทึกสถานะ
- ตรวจสอบสถานะคำขอที่รอผลจาก Payment Gateway
### Out of scope
- คำนวณค่าปรับจากการคืนหนังสือ (UC-12)
- ชำระค่าปรับเพียงบางรายการ
- คืนเงินและออกใบเสร็จ

## Constraints
- ต้องมีค่าปรับค้างชำระ
- ค่าปรับต้องอ้างอิงอัตราและจำนวนวันที่เกินกำหนดตามกฎห้องสมุด
- ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัย
- หนึ่งชุดค่าปรับมีคำขอชำระที่มีสถานะ Pending ได้ครั้งละหนึ่งคำขอ

## Requirements
- **FR-ชำระค่าปรับออนไลน์-01** ระบบต้องแสดงรายการค่าปรับค้างชำระ โดยแต่ละรายการแสดงชื่อหนังสือ วันครบกำหนด วันที่คืน จำนวนวันที่เกินกำหนด และยอดค่าปรับ พร้อมแสดงยอดรวมและช่องทางชำระเงินที่เลือกก่อนยืนยัน ผู้ใช้ต้องชำระค่าปรับค้างทั้งหมดในครั้งเดียว ไม่รองรับการเลือกชำระบางรายการ
- **FR-ชำระค่าปรับออนไลน์-02** เมื่อสมาชิกยืนยันการชำระ ระบบต้องสร้าง `payment_ref` ที่ไม่ซ้ำกัน ผูกกับรหัสสมาชิก รายการค่าปรับ และยอดรวม แล้วส่งคำขอพร้อม `payment_ref` ไปยัง Payment Gateway ผลตอบกลับต้องจับคู่ด้วย `payment_ref` และยอดเงินต้องตรงกับคำขอ หากไม่พบ ref หรือยอดไม่ตรง ระบบต้องคงสถานะคำขอและสถานะค่าปรับเดิม และบันทึกในรายการรอตรวจสอบผู้ดูแลไว้ โดยเก็บ `payment_ref` ที่ได้รับ เลขธุรกรรมของ Gateway ยอดที่ได้รับ ยอดที่คาดไว้ เหตุผล “ไม่พบ ref” หรือ “ยอดไม่ตรง” เวลาที่ได้รับ และข้อมูลดิบจาก Gateway
- **FR-ชำระค่าปรับออนไลน์-03** เมื่อได้รับผลยืนยันสำเร็จจาก Payment Gateway ที่จับคู่กับ `payment_ref` และยอดเงินถูกต้อง ระบบต้องเปลี่ยนสถานะคำขอเป็น “สำเร็จ” เปลี่ยนสถานะค่าปรับเป็น “ชำระแล้ว” บันทึกเลขธุรกรรม และบันทึกการชำระเพียงครั้งเดียว ผลสำเร็จแรกที่ได้รับไม่ว่าจะมาจาก callback หรือ polling ให้ใช้เป็นเลขธุรกรรมผลสำเร็จของคำขอนั้น ผลสำเร็จซ้ำที่มีเลขธุรกรรมเดิมต้องตอบ Gateway ด้วย HTTP 200 และข้อความยืนยันแบบเดียวกับครั้งแรก ไม่สร้างรายการธุรกรรมหรือรายการชำระใหม่ เปลี่ยนสถานะไม่ได้ และบันทึก log ว่าได้รับซ้ำเท่านั้น ถ้าเลขธุรกรรมใหม่ส่งกลับมาด้วย `payment_ref` เดิมถือว่าตัดเงินซ้ำ ให้บันทึกไว้ในรายการรอตรวจสอบเพื่อคืนเงิน โดยไม่เปลี่ยนสถานะคำขอหรือค่าปรับ
- **FR-ชำระค่าปรับออนไลน์-04** เมื่อ Payment Gateway ยืนยันว่าการชำระล้มเหลว ระบบต้องเปลี่ยนสถานะคำขอเป็น “ล้มเหลว” คงสถานะค่าปรับเป็น “ค้างชำระ” และให้สมาชิกลองใหม่ได้ หากไม่มีผลตอบกลับภายใน 30 วินาที ระบบต้องตั้งสถานะคำขอเป็น “รอยืนยันผล” (Pending) โดยคงค่าปรับเป็น “ค้างชำระ” และห้ามส่งคำขอชำระซ้ำสำหรับชุดค่าปรับเดิมขณะที่คำขอยัง Pending สมาชิกตรวจสอบสถานะได้ด้วยปุ่ม “ตรวจสอบสถานะ” ซึ่งใช้ `payment_ref` เดิมและไม่สร้างคำขอใหม่ ระบบต้องตรวจสอบสถานะกับ Gateway ทุก 5 นาที และหากครบ 30 นาทีแล้วยังไม่มีผล ให้เปลี่ยนคำขอเป็น “หมดอายุ” หลังจากนั้นสมาชิกจึงเริ่มคำขอชำระใหม่ได้ ก่อนสร้างคำขอใหม่และก่อนส่งสมาชิกไปหน้า Gateway ระบบต้องตรวจอีกครั้งว่าค่าปรับยังไม่ได้ชำระ ผลสำเร็จของคำขอเก่าที่มาถึงหลังคำขอหมดอายุต้องเปลี่ยนคำขอเป็น “สำเร็จ” และค่าปรับเป็น “ชำระแล้ว”; “หมดอายุ → สำเร็จ” เป็นการเปลี่ยนสถานะที่อนุญาตเพียงทางเดียวจากสถานะหมดอายุ หากผลสำเร็จของคำขอเก่ามาถึงขณะที่คำขอใหม่ยังไม่สำเร็จ ให้คำขอเก่าเป็น “สำเร็จ” ค่าปรับเป็น “ชำระแล้ว” และคำขอใหม่เป็น “ยกเลิก” หากคำขอเก่าและคำขอใหม่สำเร็จทั้งคู่เนื่องจากตัดเงินซ้ำ ให้ค่าปรับคงสถานะชำระครั้งเดียว ส่วนคำขอที่สำเร็จทีหลังให้สถานะ “ชำระซ้ำ – รอคืนเงิน” และแจ้งเจ้าหน้าที่
- **FR-ชำระค่าปรับออนไลน์-05** ระบบต้องให้สมาชิกเลือกหรือเปลี่ยนช่องทางชำระเงินก่อนยืนยันคำขอเท่านั้น เมื่อสร้างคำขอแล้วจะเปลี่ยนช่องทางไม่ได้ สมาชิกที่ต้องการใช้ช่องทางอื่นต้องรอให้คำขอเดิมเป็น “ล้มเหลว” หรือ “หมดอายุ” ก่อน แล้วจึงเริ่มคำขอใหม่และยืนยันช่องทางใหม่ได้

## Quality Requirements
- **NFR-SEC-01** ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัยโดยบังคับ HTTPS (TLS 1.2 ขึ้นไป) สำหรับการส่งสมาชิกไปหน้าชำระ callback และ API ที่ใช้ polling และ callback ต้องผ่านการตรวจลายเซ็นตามวิธีของ Gateway; ถ้าลายเซ็นไม่ผ่านระบบต้องปฏิเสธด้วย HTTP 401 และบันทึกเหตุผลไว้
- **NFR-REL-01** สถานะค่าปรับต้องเปลี่ยนตามผลยืนยันจาก Payment Gateway ที่จับคู่กับคำขอและยอดเงินได้ถูกต้องเท่านั้น ผลยืนยันสำเร็จที่มาถึงหลังคำขอหมดอายุต้องเปลี่ยนคำขอเป็น “สำเร็จ” และค่าปรับเป็น “ชำระแล้ว” เพราะเงินถูกตัดแล้วจริง ผลลัพธ์อื่นที่มาภายหลังห้ามเขียนทับสถานะสำเร็จ หนึ่งคำขอมี payment_ref เดียวและอนุญาตผลสำเร็จหนึ่งรายการ ถ้า Gateway ส่งเลขธุรกรรมเดิมถือว่าเป็นข้อความซ้ำและตอบรับตามปกติ แต่เลขธุรกรรมใหม่ที่ payment_ref เดิมถือว่าตัดเงินซ้ำและต้องเข้าสู่รายการรอตรวจสอบเพื่อคืนเงิน

## Acceptance Criteria
- [ ] **AC-ชำระค่าปรับออนไลน์-01** (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
  - **Given** สมาชิกมีค่าปรับค้าง 2 รายการ รวม 25 บาท
  - **When** สมาชิกยืนยันการชำระ
  - **Then** ระบบสร้าง `payment_ref` ใหม่ ส่งคำขอไปยัง Gateway และตั้งสถานะคำขอเป็น “รอยืนยันผล”
  - **When** Gateway ส่งผลสำเร็จพร้อม `payment_ref` เดิม ยอด 25 บาท และเลขธุรกรรม
  - **Then** ระบบเปลี่ยนค่าปรับทั้ง 2 รายการเป็น “ชำระแล้ว” บันทึกเลขธุรกรรม และแสดงยอดค้างเป็น 0 บาท
  - **When** Gateway ส่งผลสำเร็จซ้ำด้วยเลขธุรกรรมเดิม
  - **Then** ระบบตอบ Gateway ด้วย HTTP 200 ไม่สร้างรายการชำระหรือธุรกรรมใหม่ ไม่เปลี่ยนสถานะ และบันทึก log ว่าได้รับซ้ำ
  - **When** Gateway ส่งผลโดยไม่พบ `payment_ref` หรือยอดไม่ตรงกับยอดที่คาดไว้
  - **Then** ระบบคงสถานะคำขอและค่าปรับเดิม และสร้างรายการรอตรวจสอบผู้ดูแลพร้อมข้อมูลการตอบกลับ
- [ ] **AC-ชำระค่าปรับออนไลน์-02** (FR-ชำระค่าปรับออนไลน์-04, NFR-REL-01)
  - **Given** สมาชิกมีค่าปรับค้างชำระ
  - **When** Payment Gateway ยืนยันว่าชำระไม่สำเร็จ
  - **Then** ระบบคงค่าปรับเป็น “ค้างชำระ” และแจ้งให้สมาชิกลองใหม่ได้
  - **When** Gateway ไม่ตอบภายใน 30 วินาที
  - **Then** ระบบตั้งคำขอเป็น “รอยืนยันผล” แสดงข้อความว่ากำลังรอผล และตรวจสถานะด้วย `payment_ref` เดิมทุก 5 นาที
  - **When** ครบ 30 นาทีแล้วยังไม่มีผล
  - **Then** คำขอเป็น “หมดอายุ” และสมาชิกเริ่มคำขอใหม่ได้
  - **When** Gateway ส่งผลสำเร็จหลังคำขอหมดอายุและจับคู่ ref/ยอดได้
  - **Then** คำขอเปลี่ยนเป็น “สำเร็จ” ค่าปรับเป็น “ชำระแล้ว”
  - **When** คำขอเป็น “สำเร็จ” แต่ผลล้มเหลวส่งตามมา
  - **Then** คำขอและค่าปรับยังคงสถานะสำเร็จ
- [ ] **AC-ชำระค่าปรับออนไลน์-03** (FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05)
  - **Given** สมาชิกมีค่าปรับค้างและยังไม่ยืนยันคำขอชำระ
  - **When** สมาชิกเปลี่ยนช่องทางชำระเงิน
  - **Then** ระบบแสดงรายการค่าปรับ รายละเอียดแต่ละรายการ ยอดรวม และช่องทางที่เลือกให้ตรวจสอบก่อนยืนยัน และใช้ช่องทางใหม่นั้นเมื่อสมาชิกยืนยัน
  - **When** ระบบกำลังสร้างคำขอใหม่
  - **Then** ระบบตรวจอีกครั้งว่าค่าปรับยังไม่ชำระ ก่อนสร้างคำขอและส่งสมาชิกไปหน้า Gateway
  - **When** ผลสำเร็จของคำขอเก่าส่งมาในขณะที่คำขอใหม่ยังไม่สำเร็จ
  - **Then** คำขอเก่าเป็น “สำเร็จ” ค่าปรับเป็น “ชำระแล้ว” และคำขอใหม่เป็น “ยกเลิก”
  - **When** คำขอเก่าและคำขอใหม่ส่งผลสำเร็จทั้งคู่จากการตัดเงินซ้ำ
  - **Then** ค่าปรับชำระครั้งเดียว คำขอที่สำเร็จทีหลังมีสถานะ “ชำระซ้ำ – รอคืนเงิน” และมีการแจ้งเจ้าหน้าที่

## Assumptions
- **ASM-01** เมื่อสมาชิกเปลี่ยนช่องทางชำระเงิน สมาชิกต้องยืนยันก่อนที่ระบบจะใช้ช่องทางใหม่ในคำขอชำระ
- **ASM-02** สมาชิกเป็น Primary Actor และ Payment Gateway เป็น Secondary Actor เนื่องจากสมาชิกเริ่ม use case ส่วน Gateway ส่งผลการชำระกลับ
- **ASM-03** สถานะคำขอ Pending เปลี่ยนเป็น “สำเร็จ”, “ล้มเหลว” หรือ “หมดอายุ”; หากผลสำเร็จที่ตรวจสอบและจับคู่ได้มาถึงหลังหมดอายุ ให้เปลี่ยนเป็น “สำเร็จ” ได้ ส่วนผลลัพธ์อื่นห้ามเขียนทับสถานะสำเร็จ
- **ASM-04** ระบบตรวจสถานะคำขอ Pending ทุก 5 นาทีจนครบ 30 นาที และการตรวจจากผู้ใช้ใช้ `payment_ref` เดิม
- **ASM-05** หนึ่งชุดค่าปรับชำระรวมทั้งหมดในครั้งเดียว ไม่มีการเลือกชำระบางรายการ
- **ASM-06** การคืนเงินและการออกใบเสร็จไม่อยู่ในขอบเขตฟีเจอร์นี้
- **ASM-07** ผลสำเร็จที่มาหลังหมดอายุต้องได้รับการยอมรับเพราะเงินถูกตัดแล้วจริง และอนุญาตการเปลี่ยนสถานะจาก “หมดอายุ” เป็น “สำเร็จ” เท่านั้น
- **ASM-08** หนึ่งชุดค่าปรับมีคำขอ “รอยืนยันผล” ได้ครั้งละหนึ่งคำขอ และต้องตรวจว่าค่าปรับยังค้างชำระก่อนสร้างคำขอใหม่และก่อนส่งไปหน้า Gateway
- **ASM-09** เมื่อคำขอเก่าสำเร็จขณะคำขอใหม่ยังไม่สำเร็จ ให้คำขอเก่าเป็น “สำเร็จ” ค่าปรับเป็น “ชำระแล้ว” และคำขอใหม่เป็น “ยกเลิก”
- **ASM-10** เมื่อคำขอเก่าและคำขอใหม่ตัดเงินสำเร็จทั้งคู่ ค่าปรับชำระครั้งเดียว ส่วนคำขอที่สำเร็จทีหลังเป็น “ชำระซ้ำ – รอคืนเงิน” และแจ้งเจ้าหน้าที่
- **ASM-11** กรณี `payment_ref` ไม่พบหรือยอดไม่ตรง ให้เก็บเป็นรายการรอตรวจสอบเจ้าหน้าที่และคงสถานะคำขอ/ค่าปรับเดิม
- **ASM-12** ผลสำเร็จซ้ำตอบ Gateway ด้วย HTTP 200 และใช้เลขธุรกรรมเดิมตรวจซ้ำโดยไม่สร้างธุรกรรมหรือรายการชำระใหม่
- **ASM-13** ผลสำเร็จหนึ่งคำขอใช้ผลแรกที่ได้รับเป็นเลขธุรกรรม; เลขธุรกรรมใหม่ที่ใช้ `payment_ref` เดิมถือว่าตัดเงินซ้ำและเข้าสู่รายการรอตรวจสอบเพื่อคืนเงิน
- **ASM-14** เจ้าหน้าที่การเงินเป็นผู้อนุมัติการยืนยันชำระหรือคืนเงิน บรรณารักษ์ดูได้อย่างเดียว และการตัดสินใจทุกครั้งต้องบันทึกผู้ทำ เวลา และเหตุผล
- **ASM-15** HTTPS ทุกช่องทางกับ Gateway ต้องเป็น TLS 1.2 ขึ้นไป และ callback ต้องผ่านการตรวจลายเซ็นก่อนตอบรับ
