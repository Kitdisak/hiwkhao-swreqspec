# Feature: ชำระค่าปรับออนไลน์
Spec ID: SPEC-ชำระค่าปรับออนไลน์-007 | Source: SRS v0.3 | Use case: UC-07
Owner: ทีม หิวข้าว | Status: Draft v2 | Updated: 2569-10-11

## Goal
สมาชิกชำระค่าปรับค้างชำระผ่าน Payment Gateway และระบบบันทึกผลการชำระ

## Primary Actor
Payment Gateway (ผู้ใช้เป็นผู้เริ่มคำขอชำระ)

## Scope
### In scope
- แสดงค่าปรับค้างชำระ
- ส่งคำขอชำระไปยัง Payment Gateway
- รับผลการชำระและบันทึกสถานะ
### Out of scope
- คำนวณค่าปรับจากการคืนหนังสือ (UC-12)

## Constraints
- ต้องมีค่าปรับค้างชำระ
- ค่าปรับต้องอ้างอิงอัตราและจำนวนวันที่เกินกำหนดตามกฎห้องสมุด
- ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัย

## Requirements
- **FR-ชำระค่าปรับออนไลน์-01** ระบบต้องแสดงยอดค่าปรับที่ค้างชำระก่อนเริ่มชำระ
- **FR-ชำระค่าปรับออนไลน์-02** ระบบต้องส่งข้อมูลการชำระไปยัง Payment Gateway
- **FR-ชำระค่าปรับออนไลน์-03** เมื่อ Gateway ยืนยันการชำระสำเร็จ ระบบต้องบันทึกการชำระและเปลี่ยนสถานะเป็น “ชำระแล้ว”
- **FR-ชำระค่าปรับออนไลน์-04** หากการชำระล้มเหลว ระบบต้องไม่เปลี่ยนสถานะเป็นชำระแล้วและต้องให้ผู้ใช้ลองใหม่ (UC-07 Exception 5a)
- **FR-ชำระค่าปรับออนไลน์-05** ระบบต้องรองรับการเปลี่ยนช่องทางการชำระเงินก่อนยืนยัน (UC-07 Alternative 4a)

## Quality Requirements
- **NFR-SEC-01** ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัย เช่น HTTPS
- **NFR-REL-01** สถานะชำระเงินต้องเปลี่ยนตามผลยืนยันจาก Payment Gateway เท่านั้น

## Acceptance Criteria
- [ ] **AC-ชำระค่าปรับออนไลน์-01** (ตรวจสอบ Requirements ที่เกี่ยวข้อง)
  - **Given** ผู้ใช้มีค่าปรับค้างชำระ
  - **When** Gateway ยืนยันว่าชำระสำเร็จ
  - **Then** ระบบบันทึกการชำระและเปลี่ยนสถานะเป็น “ชำระแล้ว”
- [ ] **AC-ชำระค่าปรับออนไลน์-02** (ตรวจสอบ Requirements ที่เกี่ยวข้อง)
  - **Given** ผู้ใช้มีค่าปรับค้างชำระ
  - **When** Gateway แจ้งว่าชำระไม่สำเร็จ
  - **Then** ระบบคงสถานะค้างชำระและแจ้งให้ลองใหม่
- [ ] **AC-ชำระค่าปรับออนไลน์-03** (FR-ชำระค่าปรับออนไลน์-05)
  - **Given** ผู้ใช้ยังไม่ยืนยันการชำระ
  - **When** ผู้ใช้เปลี่ยนช่องทางชำระเงินและยืนยันการชำระ
  - **Then** ระบบใช้ช่องทางใหม่ในคำขอชำระ

## Assumptions
- **ASM-01** เมื่อผู้ใช้เปลี่ยนช่องทางชำระเงิน ผู้ใช้ต้องยืนยันก่อนที่ระบบจะใช้ช่องทางใหม่ในคำขอชำระ

## Open Questions
- **Q-01** เมื่อ Payment Gateway ไม่ตอบหรือส่งผลล่าช้า ระบบต้องแสดงสถานะใดและผู้ใช้ควรทำอะไรต่อ? ต้องถามทีม/ผู้ดูแลการเชื่อมต่อ Payment Gateway
- **Q-02** ระบบใช้ข้อมูลใดจับคู่ผลยืนยันจาก Gateway กับคำขอและค่าปรับที่ต้องชำระ และจัดการผลยืนยันซ้ำอย่างไร? ต้องถามทีม/ผู้ดูแลการเชื่อมต่อ Payment Gateway
- **Q-03** Primary Actor คือสมาชิกผู้เริ่มชำระ หรือ Payment Gateway ในฐานะระบบภายนอกที่ส่งผลกลับ? ต้องถามทีม
- **Q-04** ต้องแสดงยอดค่าปรับและรายละเอียดใดเพื่อให้ผู้ใช้ยืนยันรายการที่กำลังชำระ? ต้องถามทีม/ผู้รับผิดชอบนโยบายค่าปรับ
- **Q-05** AC แต่ละข้อควรอ้างอิง FR/NFR ID ใด และ AC-01 ควรระบุคำขอที่ส่งให้ Gateway ก่อนการยืนยันผลอย่างไร? ต้องถามทีม
