# Feature: ชำระค่าปรับออนไลน์
Spec ID: SPEC-ชำระค่าปรับออนไลน์-007 | Source: SRS v0.3 | Use case: UC-07
Owner: ทีม หิวข้าว | Status: Draft v2 | Updated: 2569-11-16

## Goal
สมาชิกชำระค่าปรับค้างชำระผ่าน Payment Gateway และระบบบันทึกผลการชำระ

## Primary Actor
สมาชิก

## Secondary Actor
Payment Gateway

## Scope
### In scope
- แสดงรายการค่าปรับค้างชำระ รายละเอียดแต่ละรายการ และยอดรวมก่อนเริ่มชำระ
- ส่งคำขอชำระไปยัง Payment Gateway
- รับผลการชำระและบันทึกสถานะ
- ตรวจสอบสถานะคำขอที่รอผลจาก Payment Gateway
### Out of scope
- คำนวณค่าปรับจากการคืนหนังสือ (UC-12)
- ชำระค่าปรับเพียงบางรายการ
- คืนเงินและออกใบเสร็จ

## Constraints
- ต้องมีค่าปรับค้างชำระ
- ค่าปรับต้องอ้างอิงอัตราและจำนวนวันที่เกินกำหนดตามกฎห้องสมุด
- ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัย
- หนึ่งชุดค่าปรับมีคำขอชำระที่มีสถานะ Pending ได้ครั้งละหนึ่งคำขอ

## Requirements
- **FR-ชำระค่าปรับออนไลน์-01** ระบบต้องแสดงรายการค่าปรับค้างชำระ โดยแต่ละรายการแสดงชื่อหนังสือ วันครบกำหนด วันที่คืน จำนวนวันที่เกินกำหนด และยอดค่าปรับ พร้อมแสดงยอดรวมและช่องทางชำระเงินที่เลือกก่อนยืนยัน ผู้ใช้ต้องชำระค่าปรับค้างทั้งหมดในครั้งเดียว ไม่รองรับการเลือกชำระบางรายการ
- **FR-ชำระค่าปรับออนไลน์-02** เมื่อสมาชิกยืนยันการชำระ ระบบต้องสร้าง `payment_ref` ที่ไม่ซ้ำกัน ผูกกับรหัสสมาชิก รายการค่าปรับ และยอดรวม แล้วส่งคำขอพร้อม `payment_ref` ไปยัง Payment Gateway ผลตอบกลับต้องจับคู่ด้วย `payment_ref` และยอดเงินต้องตรงกับคำขอ หากไม่พบ ref หรือยอดไม่ตรง ระบบต้องคงสถานะเดิมและบันทึกรายการไว้ให้ตรวจสอบ
- **FR-ชำระค่าปรับออนไลน์-03** เมื่อได้รับผลยืนยันสำเร็จจาก Payment Gateway ที่จับคู่กับ `payment_ref` และยอดเงินได้ถูกต้อง ระบบต้องเปลี่ยนสถานะคำขอเป็น “สำเร็จ” เปลี่ยนสถานะค่าปรับเป็น “ชำระแล้ว” บันทึกเลขธุรกรรม และบันทึกการชำระเพียงครั้งเดียว ผลสำเร็จที่มาซ้ำต้องไม่สร้างรายการชำระซ้ำ แต่ระบบต้องตอบรับ Gateway ตามปกติ
- **FR-ชำระค่าปรับออนไลน์-04** เมื่อ Payment Gateway ยืนยันว่าการชำระล้มเหลว ระบบต้องเปลี่ยนสถานะคำขอเป็น “ล้มเหลว” คงสถานะค่าปรับเป็น “ค้างชำระ” และให้สมาชิกลองใหม่ได้ หากไม่มีผลตอบกลับภายใน 30 วินาที ระบบต้องตั้งสถานะคำขอเป็น “รอยืนยันผล” (Pending) โดยคงค่าปรับเป็น “ค้างชำระ” และห้ามส่งคำขอชำระซ้ำสำหรับชุดค่าปรับเดิมขณะที่คำขอยัง Pending สมาชิกตรวจสอบสถานะได้ด้วยปุ่ม “ตรวจสอบสถานะ” ซึ่งใช้ `payment_ref` เดิมและไม่สร้างคำขอใหม่ ระบบต้องตรวจสอบสถานะกับ Gateway ทุก 5 นาที และหากครบ 30 นาทีแล้วยังไม่มีผล ให้เปลี่ยนคำขอเป็น “หมดอายุ” หลังจากนั้นสมาชิกจึงเริ่มคำขอชำระใหม่ได้
- **FR-ชำระค่าปรับออนไลน์-05** ระบบต้องให้สมาชิกเลือกหรือเปลี่ยนช่องทางชำระเงินก่อนยืนยันคำขอเท่านั้น เมื่อสร้างคำขอแล้วจะเปลี่ยนช่องทางไม่ได้ สมาชิกที่ต้องการใช้ช่องทางอื่นต้องรอให้คำขอเดิมเป็น “ล้มเหลว” หรือ “หมดอายุ” ก่อน แล้วจึงเริ่มคำขอใหม่และยืนยันช่องทางใหม่ได้

## Quality Requirements
- **NFR-SEC-01** ข้อมูลการชำระเงินต้องส่งผ่านช่องทางที่ปลอดภัย เช่น HTTPS
- **NFR-REL-01** สถานะค่าปรับต้องเปลี่ยนตามผลยืนยันจาก Payment Gateway ที่จับคู่กับคำขอและยอดเงินได้ถูกต้องเท่านั้น ผลยืนยันสำเร็จที่มาถึงหลังคำขอหมดอายุยังต้องได้รับการยอมรับ เพราะเงินถูกตัดแล้วจริง และต้องเปลี่ยนสถานะค่าปรับเป็น “ชำระแล้ว”; ผลลัพธ์อื่นที่มาภายหลังห้ามเขียนทับสถานะสำเร็จ

## Acceptance Criteria
- [ ] **AC-ชำระค่าปรับออนไลน์-01** (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
  - **Given** สมาชิกมีค่าปรับค้าง 2 รายการ รวม 25 บาท
  - **When** สมาชิกยืนยันการชำระ
  - **Then** ระบบสร้าง `payment_ref` ใหม่ ส่งคำขอไปยัง Gateway และตั้งสถานะคำขอเป็น “รอยืนยันผล”
  - **When** Gateway ส่งผลสำเร็จพร้อม `payment_ref` เดิม ยอด 25 บาท และเลขธุรกรรม
  - **Then** ระบบเปลี่ยนค่าปรับทั้ง 2 รายการเป็น “ชำระแล้ว” บันทึกเลขธุรกรรม และแสดงยอดค้างเป็น 0 บาท
- [ ] **AC-ชำระค่าปรับออนไลน์-02** (FR-ชำระค่าปรับออนไลน์-04, NFR-REL-01)
  - **Given** สมาชิกมีค่าปรับค้างชำระ
  - **When** Payment Gateway ยืนยันว่าชำระไม่สำเร็จ
  - **Then** ระบบคงค่าปรับเป็น “ค้างชำระ” และแจ้งให้สมาชิกลองใหม่ได้
- [ ] **AC-ชำระค่าปรับออนไลน์-03** (FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-05)
  - **Given** สมาชิกมีค่าปรับค้างและยังไม่ยืนยันคำขอชำระ
  - **When** สมาชิกเปลี่ยนช่องทางชำระเงิน
  - **Then** ระบบแสดงรายการค่าปรับ รายละเอียดแต่ละรายการ ยอดรวม และช่องทางที่เลือกให้ตรวจสอบก่อนยืนยัน และใช้ช่องทางใหม่นั้นเมื่อสมาชิกยืนยัน

## Assumptions
- **ASM-01** เมื่อสมาชิกเปลี่ยนช่องทางชำระเงิน สมาชิกต้องยืนยันก่อนที่ระบบจะใช้ช่องทางใหม่ในคำขอชำระ
- **ASM-02** สมาชิกเป็น Primary Actor และ Payment Gateway เป็น Secondary Actor เนื่องจากสมาชิกเริ่ม use case ส่วน Gateway ส่งผลการชำระกลับ
- **ASM-03** สถานะคำขอ Pending เปลี่ยนเป็น “สำเร็จ”, “ล้มเหลว” หรือ “หมดอายุ”; หากผลสำเร็จที่ตรวจสอบและจับคู่ได้มาถึงหลังหมดอายุ ให้เปลี่ยนเป็น “สำเร็จ” ได้ ส่วนผลลัพธ์อื่นห้ามเขียนทับสถานะสำเร็จ
- **ASM-04** ระบบตรวจสถานะคำขอ Pending ทุก 5 นาทีจนครบ 30 นาที และการตรวจจากผู้ใช้ใช้ `payment_ref` เดิม
- **ASM-05** หนึ่งชุดค่าปรับชำระรวมทั้งหมดในครั้งเดียว ไม่มีการเลือกชำระบางรายการ
- **ASM-06** การคืนเงินและการออกใบเสร็จไม่อยู่ในขอบเขตฟีเจอร์นี้

## Open Questions
- **Q-07** อัตราค่าปรับต่อวันและวิธีคำนวณยอดค่าปรับต่อรายการกำหนดอย่างไร? ต้องถามบรรณารักษ์/ผู้กำหนดนโยบายค่าปรับ
- **Q-08** จะยืนยันการตรวจผลสำเร็จซ้ำและกรณีไม่มีผลตอบกลับจนคำขอหมดอายุด้วย AC เดิมข้อใด หรือทีมต้องอนุมัติการเพิ่ม AC ใหม่ก่อน? ต้องถามทีม
