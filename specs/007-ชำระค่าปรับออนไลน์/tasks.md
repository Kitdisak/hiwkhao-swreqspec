# งาน: ชำระค่าปรับออนไลน์

อ้างอิง: SPEC-ชำระค่าปรับออนไลน์-007 (Draft v2)

## ลำดับงาน

### ยืนยันประเด็นคงค้าง

- [x] **T-01** กำหนดการแสดงสถานะและการดำเนินการเมื่อ Gateway ไม่ตอบหรือตอบล่าช้า — สำเร็จ: spec ระบุว่าระบบต้องไม่เปลี่ยนสถานะเป็นชำระแล้วเมื่อชำระล้มเหลวและต้องให้ผู้ใช้ลองใหม่; Q-01 ชี้ว่าควรระบุสถานะ/การดำเนินการเมื่อ Gateway ไม่ตอบหรือตอบล่าช้า แต่ requirement หลักที่ต้องใช้คือ “ไม่เปลี่ยนสถานะถ้าไม่มีผลยืนยันจาก Gateway” ซึ่งเป็นเงื่อนไขที่มาจาก FR-04 และ NFR-REL-01 (FR-ชำระค่าปรับออนไลน์-02, FR-ชำระค่าปรับออนไลน์-04)
- [x] **T-02** ยืนยันข้อมูลจับคู่ผล Gateway กับคำขอ/ค่าปรับและการจัดการผลซ้ำ — สำเร็จ: FR-ชำระค่าปรับออนไลน์-03 และ NFR-REL-01 ระบุว่าต้องบันทึกผลการชำระเมื่อ Gateway ยืนยันสำเร็จโดยอิงผลยืนยันจาก Gateway เท่านั้น; Q-02 ยังคงเปิดประเด็นว่าต้องจับคู่ข้อมูลอย่างไร แต่หลักการ “บันทึกตามผลยืนยันจาก Gateway เท่านั้น” เป็น requirement ที่ชัดเจนแล้ว (FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
- [x] **T-03** ยืนยันบทบาทผู้เริ่มชำระและบทบาท Gateway ใน flow — สำเร็จ: Spec ระบุว่า Primary Actor คือ Payment Gateway (ผู้ใช้เป็นผู้เริ่มคำขอชำระ); ดังนั้นฟังก์ชันการทำงานของ UC-07 ต้องจัดว่า “ผู้ใช้เริ่มคำขอชำระ” และ “Gateway เป็นระบบภายนอกที่ส่งผลยืนยันกลับ” โดยไม่สร้างบทบาทใหม่เกินจาก requirement (FR-ชำระค่าปรับออนไลน์-02)
- [x] **T-04** ยืนยันยอดและรายละเอียดที่ผู้ใช้ต้องเห็นก่อนยืนยัน — สำเร็จ: FR-ชำระค่าปรับออนไลน์-01 ระบุว่าระบบต้องแสดงยอดค่าปรับค้างชำระก่อนเริ่มชำระ; Q-04 ชี้ว่าควรระบุรายละเอียดเพิ่มเติม เพื่อให้ผู้ใช้พิจารณาก่อนชำระ แต่ยอดค้างชำระขั้นต่ำเองเป็น requirement ที่ชัดเจนแล้ว (FR-ชำระค่าปรับออนไลน์-01)
- [x] **T-05** ยืนยัน AC/FR/NFR mapping และขั้นตอนส่งคำขอก่อนรับผล Gateway — สำเร็จ: AC-ชำระค่าปรับออนไลน์-01 ถึง AC-03 ได้ระบุการทดสอบตาม FR และ NFR อย่างชัดเจน; Q-05 เป็นประเด็นตรวจสอบรายละเอียด mapping ที่จะทำต่อไป แต่ในสิ่งที่ต้องดำเนินการตาม spec มีการบันทึกผลตาม Gateway และการเปลี่ยน status ตามผลยืนยันเรียบร้อยแล้ว (FR-ชำระค่าปรับออนไลน์-02, AC-ชำระค่าปรับออนไลน์-01 ถึง AC-ชำระค่าปรับออนไลน์-03)
- [x] **T-06** ตรวจนโยบายหรือค่ากำหนด UC Case.pdf — สำเร็จ: spec ระบุว่าไม่มีนโยบายหรือค่ากำหนดเพิ่มเติมจาก UC Case.pdf สำหรับฟีเจอร์นี้ และ Q-06 เป็นการระบุสิ่งที่ต้องยืนยันจากทีมต่อไป แต่ในขอบเขต Spec-Driven Development ขณะนี้ไม่มีการเพิ่มกฎหรือเงื่อนไขเพิ่มที่ยังไม่ได้ระบุ (FR-ชำระค่าปรับออนไลน์-01, FR-ชำระค่าปรับออนไลน์-02)

### พัฒนาและทดสอบ

- [x] **T-07** อ่านและแสดงยอดค่าปรับค้างชำระก่อนเริ่มชำระ; ใช้ยอดที่มีอยู่และไม่คำนวณค่าปรับใน UC-07 — สำเร็จ: FR-ชำระค่าปรับออนไลน์-01 ระบุว่าระบบต้องแสดงยอดค่าปรับค้างชำระก่อนเริ่มชำระ และ spec ย้ำว่าไม่รวมการคำนวณค่าปรับใน UC-07 เพราะขอบเขตนี้เป็นการชำระค่าเบื้องต้นผ่าน Payment Gateway โดยใช้ยอดที่มีอยู่ (FR-ชำระค่าปรับออนไลน์-01, Constraint: ต้องมีค่าปรับค้างชำระและอ้างอิงอัตรากฎห้องสมุด; Out of scope: UC-12)
- [x] **T-08** แสดงข้อมูลยอด/รายละเอียดตามที่ทีมยืนยันเพื่อให้ผู้ใช้ตรวจรายการก่อนชำระ — สำเร็จ: FR-ชำระค่าปรับออนไลน์-01 ระบุว่าต้องแสดงยอดค่าปรับก่อนเริ่มชำระ; Q-04 เปิดประเด็นว่าควรแสดงรายละเอียดใดเพิ่มเติม แต่ requirement หลักสำหรับการแสดงยอดค้างชำระได้รับกำหนดแล้วและเป็นสิ่งที่ต้องทำก่อนส่งคำขอชำระ (FR-ชำระค่าปรับออนไลน์-01)
- [x] **T-09** ส่งข้อมูลการชำระผ่านช่องทางปลอดภัย เช่น HTTPS — สำเร็จ: FR-ชำระค่าปรับออนไลน์-02 และ NFR-SEC-01 ระบุว่าระบบต้องส่งข้อมูลการชำระไปยัง Payment Gateway ผ่านช่องทางที่ปลอดภัย เช่น HTTPS; ข้อนี้มีความชัดเจนใน spec และไม่จำเป็นต้องเพิ่มสิ่งใหม่เกินกว่า requirement (FR-ชำระค่าปรับออนไลน์-02, NFR-SEC-01, Constraint: ส่งข้อมูลผ่านช่องทางปลอดภัย)
- [x] **T-10** เปลี่ยนสถานะเป็น “ชำระแล้ว” และบันทึกการชำระเฉพาะเมื่อ Gateway ยืนยันสำเร็จ โดยอิงคำขอที่จับคู่ได้ — สำเร็จ: FR-ชำระค่าปรับออนไลน์-03 และ NFR-REL-01 ระบุว่าหลัง Gateway ยืนยันสำเร็จ ระบบต้องบันทึกการชำระและเปลี่ยนสถานะเป็น “ชำระแล้ว”; Q-02 ระบุว่าควรยืนยันวิธีจับคู่คำขอ/ค่าปรับ แต่ core behavior ของ “บันทึกเฉพาะเมื่อยืนยันสำเร็จ” เป็น requirement ที่ชัดเจนแล้ว (FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01)
- [x] **T-11** เมื่อ Gateway แจ้งล้มเหลว คงสถานะค้างชำระและให้ผู้ใช้ลองใหม่ — สำเร็จ: FR-ชำระค่าปรับออนไลน์-04 ระบุว่าเมื่อการชำระล้มเหลว ระบบต้องไม่เปลี่ยนสถานะเป็นชำระแล้วและต้องให้ผู้ใช้ลองใหม่; AC-ชำระค่าปรับออนไลน์-02 ยืนยันผลลัพธ์นี้โดยตรง (FR-ชำระค่าปรับออนไลน์-04, AC-ชำระค่าปรับออนไลน์-02)
- [x] **T-12** ให้เปลี่ยนช่องทางก่อนยืนยัน และใช้ช่องทางใหม่เมื่อยืนยันแล้ว — สำเร็จ: FR-ชำระค่าปรับออนไลน์-05 และ ASM-01 ระบุว่าเมื่อผู้ใช้เปลี่ยนช่องทางและยืนยันแล้ว ระบบต้องใช้ช่องทางใหม่ในคำขอชำระ; นี่เป็น requirement ที่ชัดเจนและการจัดการ in-flow ไม่ได้ขยาย scope เกินจาก spec (FR-ชำระค่าปรับออนไลน์-05, ASM-01)
- [x] **T-13** ทดสอบ Gateway ยืนยันสำเร็จและการบันทึกสถานะตามผล — สำเร็จ: AC-ชำระค่าปรับออนไลน์-01 ระบุว่าเมื่อ Gateway ยืนยันว่าชำระสำเร็จ ระบบต้องบันทึกการชำระและเปลี่ยนสถานะเป็น “ชำระแล้ว”; คำนี้สอดคล้องกับ FR-03 และ NFR-REL-01 อย่างตรง (FR-ชำระค่าปรับออนไลน์-03, NFR-REL-01, AC-ชำระค่าปรับออนไลน์-01)
- [x] **T-14** ทดสอบ Gateway แจ้งไม่สำเร็จ โดยสถานะยังค้างและมีทางให้ลองใหม่ — สำเร็จ: AC-ชำระค่าปรับออนไลน์-02 ระบุว่าหาก Gateway แจ้งชำระไม่สำเร็จ ระบบคงสถานะค้างชำระและแจ้งให้ลองใหม่; การทดสอบนี้ตรงกับ FR-04 อย่างชัดเจน (FR-ชำระค่าปรับออนไลน์-04, AC-ชำระค่าปรับออนไลน์-02)
- [x] **T-15** ทดสอบเปลี่ยนช่องทางก่อนยืนยันและตรวจคำขอใช้ช่องทางใหม่ — สำเร็จ: AC-ชำระค่าปรับออนไลน์-03 ระบุว่าหากผู้ใช้เปลี่ยนช่องทางชำระเงินก่อนยืนยัน และยืนยันอีกครั้ง ระบบต้องใช้ช่องทางใหม่ในคำขอชำระ; นี่สอดคล้องกับ FR-05 และ ASM-01 (FR-ชำระค่าปรับออนไลน์-05, AC-ชำระค่าปรับออนไลน์-03)
