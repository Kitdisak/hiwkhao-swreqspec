# แผนงาน: ติดตามสถานะการจองหนังสือ

อ้างอิง: SPEC-ติดตามสถานะการจองหนังสือ-005 (Draft v2)

## 1. สรุปแนวทาง

- นักศึกษา/สมาชิกที่เข้าสู่ระบบเปิดหน้ารายการจองของฉันเพื่อดูรายการจองทั้งหมดที่มีอยู่ในสามสถานะ (FR-ติดตามสถานะการจองหนังสือ-01, ASM-01).
- แสดงชื่อหนังสือ ผู้แต่ง วันที่จอง และสถานะเป็นข้อความ โดยไม่แสดงรหัสประจำเล่ม (FR-ติดตามสถานะการจองหนังสือ-01, FR-ติดตามสถานะการจองหนังสือ-02, ASM-09).
- อ่านข้อมูลจาก server ทุกครั้งที่เปิดหน้า ไม่ใช้ cache และไม่ refresh อัตโนมัติระหว่างเปิดหน้าค้างไว้ (NFR-ACC-01, ASM-03).
- คำนวณคิว Waiting แยกตามชื่อเรื่องด้วยกติกาเดียวกับ SPEC-004 และแสดงวันหมดเขตเฉพาะ Ready ที่มีข้อมูล (FR-ติดตามสถานะการจองหนังสือ-02, FR-ติดตามสถานะการจองหนังสือ-03, ASM-08).
- แสดงข้อความเมื่อไม่มีรายการ; ไม่ทำการสร้าง ยกเลิก ลบ หรือซ่อนรายการจอง (FR-ติดตามสถานะการจองหนังสือ-04, ASM-01, ASM-07).

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) สำหรับหน้าบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | เป็นค่าเริ่มต้นตามรายวิชาและสอดคล้องกับ frontend ที่ repository ใช้อยู่ |
| Python FastAPI สำหรับหลังบ้าน | **ทีมเลือกเอง ไม่ได้มาจาก spec** | เป็นค่าเริ่มต้นตามรายวิชาและสอดคล้องกับ backend ที่ repository ใช้อยู่ |
| SQLite สำหรับข้อมูลการจอง | **ทีมเลือกเอง ไม่ได้มาจาก spec** | ใช้ฐานข้อมูลที่บริการจองหนังสือของ SPEC-004 ใช้อยู่แล้ว; เพิ่มฟิลด์วันหมดเขตแบบ nullable เพื่อรองรับ FR-ติดตามสถานะการจองหนังสือ-03 |

Constraints ใน SPEC-005 ไม่ระบุเทคโนโลยีหรือมี ID เฉพาะ.

## 3. โมเดลข้อมูล

| Entity / แหล่งข้อมูล | ฟิลด์หลัก | รองรับ |
|---|---|---|
| Reservation (ข้อมูลเดิมและ read model) | reservation_id (ตัวระบุภายใน), member_id, title_id, status, recorded_at, pickup_deadline (nullable); ใช้ first_name, last_name, member_code ที่บันทึกไว้เพื่อจัดลำดับคิว | FR-ติดตามสถานะการจองหนังสือ-01, FR-ติดตามสถานะการจองหนังสือ-02, FR-ติดตามสถานะการจองหนังสือ-03, ASM-01, ASM-08, ASM-09 |
| CatalogRecord (ข้อมูลอ้างอิง) | book_id/title_id, title, authors | แปลง title_id เป็นชื่อหนังสือและผู้แต่ง; ไม่อ่านหรือแสดงรหัสประจำเล่ม (FR-ติดตามสถานะการจองหนังสือ-01, ASM-09) |
| Authenticated user/session | member_id จาก session ที่เข้าสู่ระบบ | ใช้กรองรายการให้เป็นของผู้ใช้ปัจจุบัน (Constraint: ผู้ใช้ต้องเข้าสู่ระบบ, FR-ติดตามสถานะการจองหนังสือ-01) |

วันที่จองแสดงจาก recorded_at โดยแปลงเป็นเขตเวลา Asia/Bangkok และรูปแบบภาษาไทย “20 พ.ย. 2569”; วันหมดเขตคงเป็น optional และแสดงตาม FR-ติดตามสถานะการจองหนังสือ-03 (NFR-USE-01, ASM-04, ASM-05). ไม่เพิ่มฟิลด์หรือพฤติกรรมเพื่อกำหนดอายุการเก็บหรือการลบรายการ (ASM-01, Q-01).

## 4. API / หน้าจอ

| รายการ | Method / path หรือ input/output หลัก | รองรับ |
|---|---|---|
| รายการจองของผู้ใช้ปัจจุบัน | `GET /api/me/reservations`; input: session cookie; output: รายการของผู้ใช้ปัจจุบัน โดยแต่ละรายการมี title, authors, recorded_at, status, queue_position เฉพาะ Waiting และ pickup_deadline เฉพาะ Ready ที่มีข้อมูล; ตั้ง `Cache-Control: no-store` | FR-ติดตามสถานะการจองหนังสือ-01 ถึง FR-ติดตามสถานะการจองหนังสือ-03, NFR-ACC-01, ASM-03, ASM-08, ASM-09 |
| หน้ารายการจองของฉัน | หน้า route `/my-reservations` พร้อมลิงก์เข้าถึงจากหน้าหลักที่มีอยู่; แสดงชื่อหนังสือ ผู้แต่ง วันที่จอง สถานะ คิว และวันหมดเขตตามเงื่อนไข; เมื่อไม่พบรายการแสดงข้อความว่าไม่มีรายการ | FR-ติดตามสถานะการจองหนังสือ-01 ถึง FR-ติดตามสถานะการจองหนังสือ-04, NFR-USE-01, AC-ติดตามสถานะการจองหนังสือ-01 ถึง AC-ติดตามสถานะการจองหนังสือ-03 |

API ต้องปฏิเสธคำขอที่ไม่มี session ตาม Constraint เรื่องการเข้าสู่ระบบ. หน้าเว็บไม่ทำ polling ระหว่างเปิดหน้าค้างไว้ (NFR-ACC-01, ASM-03). ไม่มี endpoint สำหรับสร้าง ยกเลิก ลบ หรือซ่อนรายการในฟีเจอร์นี้ (ASM-01, ASM-07).

## 5. ตารางตรวจ Constraints

Constraints ใน spec ไม่มี ID เฉพาะ จึงอ้างอิงด้วยข้อความ Constraint เดิม ไม่สร้าง ID ใหม่.

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ไม่มี ID: ผู้ใช้ต้องเข้าสู่ระบบ | อ่าน session cookie ใน `GET /api/me/reservations` และคืนเฉพาะรายการที่ member_id ตรงกับผู้ใช้ปัจจุบัน | ใช้แล้ว |
| ไม่มี ID: สถานะต้องตรงกับข้อมูลการจองล่าสุด | Query ข้อมูลจาก server ทุกครั้งที่เปิดหน้า; ปิด browser caching และไม่ทำ auto-refresh ระหว่างเปิดหน้าค้างไว้ (NFR-ACC-01, ASM-03) | ใช้แล้ว |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-ติดตามสถานะการจองหนังสือ-01 | `test_AC_ติดตามสถานะการจองหนังสือ_01` | สร้างข้อมูล Waiting, Ready และ Completed ของผู้ใช้ที่เข้าสู่ระบบ รวมข้อมูลของผู้ใช้อื่นเพื่อยืนยันการกรอง; เรียก API และเปิดหน้าเพื่อตรวจรายการทั้งหมดของผู้ใช้ ชื่อหนังสือ ผู้แต่ง วันที่จอง สถานะ และคิวเฉพาะ Waiting; เปลี่ยนข้อมูล server แล้วเปิดหน้าใหม่เพื่อตรวจว่าอ่านสถานะและคิวล่าสุด (FR-ติดตามสถานะการจองหนังสือ-01, FR-ติดตามสถานะการจองหนังสือ-02, NFR-ACC-01, ASM-01, ASM-03, ASM-08, ASM-09) |
| AC-ติดตามสถานะการจองหนังสือ-02 | `test_AC_ติดตามสถานะการจองหนังสือ_02_1` | เตรียมรายการ Ready ที่มีวันหมดเขต 20 พฤศจิกายน 2569 แล้วตรวจหน้าเว็บแสดงข้อความ “20 พ.ย. 2569” (FR-ติดตามสถานะการจองหนังสือ-03, NFR-USE-01, ASM-04, ASM-05) |
| AC-ติดตามสถานะการจองหนังสือ-02 | `test_AC_ติดตามสถานะการจองหนังสือ_02_2` | เตรียมรายการ Ready ที่ไม่มีวันหมดเขต แล้วตรวจว่าแสดงสถานะ Ready แต่ไม่มีวัน ป้ายกำกับ ช่อง หรือข้อความทดแทน (FR-ติดตามสถานะการจองหนังสือ-03, ASM-04) |
| AC-ติดตามสถานะการจองหนังสือ-02 | `test_AC_ติดตามสถานะการจองหนังสือ_02_3` | เตรียมรายการ Waiting และ Completed ที่มีวันหมดเขต แล้วตรวจว่าไม่แสดงวันหมดเขต (FR-ติดตามสถานะการจองหนังสือ-03, ASM-04) |
| AC-ติดตามสถานะการจองหนังสือ-03 | `test_AC_ติดตามสถานะการจองหนังสือ_03` | ใช้ผู้ใช้ที่เข้าสู่ระบบและไม่มีรายการจอง; ตรวจ API คืนรายการว่างและหน้าเว็บแจ้งว่าไม่มีรายการ (FR-ติดตามสถานะการจองหนังสือ-04) |

เพิ่มการตรวจ authentication และ response `Cache-Control: no-store` เพื่อยืนยัน Constraints และ NFR-ACC-01. Repository มี pytest สำหรับ backend แต่ยังไม่มี frontend test runner; จึงใช้ pytest สำหรับ API และ browser แบบ manual สำหรับผลการแสดงผล AC จนกว่าทีมจะเลือกเพิ่ม tooling.

## 7. ลำดับงาน

1. ตรวจ schema และบริการ Reservation, session ผู้ใช้ และ catalog ที่มีอยู่ เพื่อกำหนดการอ่านข้อมูลโดยไม่สร้าง flow จองใหม่ (FR-ติดตามสถานะการจองหนังสือ-01, Constraint: ผู้ใช้ต้องเข้าสู่ระบบ).
2. เพิ่มฟิลด์ pickup_deadline แบบ nullable ใน read model/storage พร้อมรองรับข้อมูลเดิมที่ไม่มีวันหมดเขต (FR-ติดตามสถานะการจองหนังสือ-03, ASM-04).
3. เพิ่ม service สำหรับอ่านรายการของผู้ใช้ปัจจุบันและ map ชื่อหนังสือ/ผู้แต่งจาก CatalogRecord (FR-ติดตามสถานะการจองหนังสือ-01, ASM-01, ASM-09).
4. คำนวณ queue_position ใหม่สำหรับ Waiting แยกตามชื่อเรื่อง โดยใช้ comparator และ tie-break เดียวกับ SPEC-004 (FR-ติดตามสถานะการจองหนังสือ-02, ASM-02, ASM-08).
5. เพิ่ม `GET /api/me/reservations` ที่ตรวจ session, คืนข้อมูลล่าสุด และปิด caching (Constraint: ผู้ใช้ต้องเข้าสู่ระบบ, NFR-ACC-01, ASM-03).
6. เพิ่ม route `/my-reservations` และลิงก์จากหน้าหลัก; แสดง title, authors, reservation date ในเวลา Asia/Bangkok, status, คิวเฉพาะ Waiting และ deadline เฉพาะ Ready (FR-ติดตามสถานะการจองหนังสือ-01 ถึง FR-ติดตามสถานะการจองหนังสือ-03, NFR-USE-01, ASM-04, ASM-05, ASM-09).
7. แสดง empty state เมื่อรายการจองว่าง โดยไม่เพิ่มการสร้างหรือยกเลิกรายการ (FR-ติดตามสถานะการจองหนังสือ-04, ASM-07).
8. เพิ่ม pytest สำหรับ API/ข้อมูลและตรวจ UI ใน browser ตาม AC ทั้งสามข้อ; ยืนยันว่าไม่มีการแสดงรหัสประจำเล่มหรือข้อมูลจากผู้ใช้อื่น (AC-ติดตามสถานะการจองหนังสือ-01 ถึง AC-ติดตามสถานะการจองหนังสือ-03, ASM-09).

## 8. สิ่งที่ยังไม่ทำ

- **Q-01** นโยบายการลบรายการจองหรือการเก็บประวัติเป็นอย่างไร? ต้องถามบรรณารักษ์; คำตอบไม่กระทบการสร้างฟีเจอร์นี้ตาม ASM-01. ส่วนที่เกี่ยวข้องกับการกำหนดนโยบายลบหรืออายุการเก็บจะยังไม่สร้างจนกว่าจะได้คำตอบ.

## ประเด็นตรวจสอบสำหรับทีม

- ไม่มี Constraint ที่ยังไม่ได้ใช้; ทั้งสอง Constraint ถูกครอบคลุมใน endpoint และการแสดงข้อมูลล่าสุด.
- AC-ติดตามสถานะการจองหนังสือ-02 ทดสอบหน้าจอได้ยากกว่าข้ออื่น เพราะมี 3 เงื่อนไขการแสดงวัน และ frontend ยังไม่มี test runner; ต้องตรวจ API ด้วย pytest และผลการแสดงผลใน browser แบบ manual ตามแนวทางที่เสนอ.
- การเตรียมข้อมูล Ready พร้อม/ไม่มีวันหมดเขตและ Waiting/Completed ที่มีวันหมดเขต ต้องใช้ข้อมูลทดสอบเฉพาะ เพราะ storage ปัจจุบันยังไม่มีฟิลด์วันหมดเขต (FR-ติดตามสถานะการจองหนังสือ-03).
- ไม่อนุมานนโยบายลบหรืออายุการเก็บจาก Q-01; ตามคำตอบทีม ประเด็นนี้ไม่ขวางการสร้างฟีเจอร์แสดงรายการ (ASM-01, Q-01).
